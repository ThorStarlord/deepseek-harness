# Agent Note: 个人 Fork 的产品/设计评审治理

Status: implemented

[English](2026-11-15-fork-product-design-review-governance.md) | 中文

## 问题

这个公开的个人 fork 继承了 UI skill，其中的评审触发条件和检查标准仍然有用，但列出的产品/设计评审名单属于上游项目。该 skill 没有明确禁止名单外的评审者，却也没有规定本 fork 如何选择这类评审者或记录其身份、评审修订、发现和最终结论。GitHub 只将 fork 所有者列为协作者；默认分支没有保护规则或评审门禁。文档检查不会验证评审者资格或评审结论。因此，本 fork 缺少可靠的评审路径，而 GitHub 显示可合并也不能证明评审已经发生。

## 决策

仓库要求对大型 UI 变更和用户可明显感知的交互变更进行独立的人工产品/设计评审。所有者为每个符合条件的 pull request 指定合格评审者。评审者可以来自上游名单之外，也无需成为仓库协作者。评审投入遵循现有 UI 工作流程和[评审 UI 设计指南](../../../../docs/cookbook/reviewing-ui-design.zh.md)，并按变更的影响和风险调整。

评审者应承担相关产品或设计职责，或能证明其具有评估类似交互的经验；不得是该变更的作者或主要实现者，并应独立作出评估。Pull request 应记录评审者身份、简要的资格依据、可能影响独立性的关系、所评审的 commit SHA、检查过的交互和证据、发现、日期及最终结论。可接受正式 GitHub 评审或 pull request 顶层评论。如果这两种渠道都不可用，pull request 应链接到原始且可核实的评审记录，并注明评审者身份。

四种结论含义各不相同：**APPROVE** 表示所评审修订没有阻塞性产品/设计问题；**CHANGES REQUESTED** 记录需要修复的阻塞问题，并要求在修订后的版本上给出最终结论；**ADVISORY** 记录非阻塞建议，单独的建议不能满足评审要求；本决策不提供 **OWNER EXCEPTION**。批准适用于记录的 SHA。后续变更如果可能改变已评估结果，应重新评审。产品/设计批准不能替代技术验证或授予合并权限。

如果没有合格评审者，所有者记录这一外部依赖并保持 pull request 未合并。沉默、无人答复的请求、技术上可合并的状态以及 Agent 评估都不满足评审要求。Agent 可以协助准备证据和发现，但不能提供独立的人工批准。本决策不会批准已经打开的 pull request；每项符合条件的变更都需要单独记录结论。

## 考虑过的替代方案

- **外部合格评审者——采纳。** 外部评审者无需上游参与或协作者权限，同时能保留独立判断。评审者的可用性不固定；记录资格、独立性、SHA、证据、发现和结论，可以在基础设施成本较低的情况下追责。
- **由 fork 指定的固定评审池——不采纳。** 固定名单可能提高可用性并明确责任，但寻找和维护具备资格且独立的评审者需要投入。逐个 PR 指定评审者可以明确责任，也无需维护固定名单；所有者的提名不能证明评审者具备资格或独立性。
- **由所有者批准的替代评估——不采纳。** 仅由所有者或 Agent 评估很容易安排且协调成本较低，但会减少独立判断并带来自我批准风险。本决策不提供此类替代方式。重新考虑须另行作出明确的所有者决定，并记录在整合后的政策变更中。

## 影响

在没有固定独立评审池的个人 fork 中，仍要求合格的独立判断。外部评审者可能暂时不可用，因此符合条件的 pull request 可能保持未合并；这保留了评审要求，但无法保证交付时间。记录资格、独立性、身份、证据和评审者自己的结论，可以使逐个 PR 的评审者选择可追责，同时由评审者对其评估负责。

该流程通过文档规定，而非由机械门禁强制执行。它不更改 GitHub 权限、分支保护或协作者名单。所有者在合并前，须将 pull request 中的评审记录与技术验证分开检查。整合本政策不会追溯批准其他待审 pull request。

## 验证

UI skill 是本政策的责任文件，其中包含评审触发条件、评审者标准、可接受渠道、必需证据、结论类型及无可用评审者时的处理方式。文档门禁检查 skill 和双语 Agent Note 的格式，但不会验证评审者资格或评审结论。合并前，所有者须在每个符合条件的 pull request 中核实这些字段和所评审的 SHA。
