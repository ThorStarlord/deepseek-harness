# Agent Note: 个人 Fork 的产品/设计评审治理

Status: proposed

[English](2026-11-15-fork-product-design-review-governance.md) | 中文

## 问题

这个公开的个人 fork 继承了 UI skill，其中的评审触发条件和检查标准仍然有用，但列出的产品/设计评审名单属于上游项目。该 skill 没有明确禁止名单外的评审者，却也没有规定本 fork 如何选择这类评审者或记录其身份、评审修订、发现和最终结论。GitHub 只将 fork 所有者列为协作者；默认分支没有保护规则或评审门禁。文档检查不会验证评审者资格或评审结论。因此，本 fork 缺少可靠的评审路径，而 GitHub 显示可合并也不能证明评审已经发生。

## 提案

继续要求对大型 UI 变更和用户可明显感知的交互变更进行独立的人工产品/设计评审。仓库所有者可为每个符合条件的 PR 指定合格评审者，包括不是仓库协作者的外部评审者。上游名单可以作为候选来源，但不再是唯一来源或本 fork 必须依赖的固定名单。

评审者应承担相关产品或设计职责，或能证明其具有评估类似交互的经验；评审者不得是该变更的作者或主要实现者，并应独立作出评估。PR 应记录评审者身份、简要的资格依据、可能影响独立性的关系、所评审的 commit SHA、检查过的交互和证据、发现、日期及最终结论。可接受正式 GitHub 评审或 PR 顶层评论；两种方式都不可用时，PR 应链接到原始且可核实的评审记录，并指出评审者身份。

使用四种不同结论：**APPROVE** 表示该修订没有阻塞性产品/设计问题；**CHANGES REQUESTED** 记录阻塞问题；**ADVISORY** 记录非阻塞建议，单独的建议不能满足评审要求；**OWNER EXCEPTION** 在本提案下不可用。产品/设计批准不能替代技术验证或授予合并权限。批准只适用于记录的 SHA；如果后续变更可能改变已评估结果，应重新评审受影响的交互。采用本流程本身不会批准已经打开的 PR；每项符合条件的变更都需要单独记录评审结论。

按照现有 UI 工作流程和[评审 UI 设计指南](../../../../docs/cookbook/reviewing-ui-design.zh.md)调整评审投入。如果没有合格评审者，PR 应保持未合并状态并记录外部依赖。Agent 评估可协助准备材料，但不计作独立人工批准。任何仅由所有者评估或由 Agent 辅助的替代方式，都必须先经仓库所有者明确批准并整合一项单独的政策修订，之后才能采用。

这是一项以文档规定的人工流程。现有文档门禁会校验政策和翻译文件，但没有机械门禁会验证评审者资格或评审结论。本提案不更改 GitHub 权限、分支保护或外部协作者。

## 考虑过的替代方案

- **方案 A——外部合格评审者。** 只要评审者符合上述条件，评审质量和独立性就能保持较高水平。评审者的可用性不固定，但无需加入协作者名单，也不必来自上游。记录身份、资格、SHA、证据和结论可使评审过程可追责。基础设施成本较低，但每项 PR 都需要协调，因此适合没有独立维护者的个人 fork。
- **方案 B——由 fork 指定评审者。** 指定评审者能明确每项变更的责任人，并提高可追责性。固定评审名单可能提高可用性，但寻找、确认资格和维护名单都需要成本；如果作者评审自己的实现，也不具备独立性。本 fork 没有固定的独立评审池，因此按 PR 从方案 A 中指定人员更合适。所有者的提名不能证明评审者具备资格或独立性。
- **方案 C——由所有者批准的替代评估。** 这种方式随时可用，协调成本最低，但它以所有者或 Agent 的评估替代独立人工评审，评审质量和独立性较低。明确记录所有者理由可以提升可追责性，但仍有自我批准风险，不适合作为个人 fork 的默认方式。本提案不启用此方案；使用前必须另行制定政策修订并由所有者明确批准。

## 验收标准

- UI skill 保留评审触发条件、检查要求和按影响调整投入的规则，并明确适用于 fork 的评审者路径。
- 不在上游名单或协作者列表中的评审者，可通过身份明确的 GitHub 账号或原始且可核实的评审记录提交有效评审。
- 每项评审都记录资格依据、独立性、所评审 SHA、检查范围和证据、发现、日期及最终结论。
- 批准、要求修改、建议和所有者例外的含义互不混淆；沉默和可合并状态永远不能满足评审要求。
- 政策变更本身不会批准任何待审 PR。没有可用评审者时，PR 保持未合并状态；未经单独、明确的所有者批准，不采用仅由所有者或 Agent 辅助的替代评审。
- 政策继续由现有 skill 负责；不在 cookbook 或仓库说明中添加重复规则。
- 提案说明有结构一致的英文和简体中文版本，并维护最新的配对记录。

## 风险

- 外部评审者可能暂时不可用，PR 因此可能保持未合并状态。这保留了评审质量，但无法保证交付时间。
- 评审者由所有者选择，可能引起对偏见的担忧。记录资格、独立性、身份和评审者自己的结论，可使选择过程可追责，同时避免将提名视作批准。
- GitHub 和文档检查不会强制执行这项人工流程。合并前所有者仍须检查记录的评审结论；本提案不更改仓库设置或自动门禁。
- 长期缺少评审者时，所有者可能希望使用替代评估；但在没有单独决策的情况下开放该方式会削弱独立判断要求。在所有者明确批准一项范围有限的政策修订前，继续关闭此选项。
